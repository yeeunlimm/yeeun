# 서울 야외 팝업 장소·날짜 선정 및 리포트 흐름

작성일: 2026-09-30

## 현재 알고 있는 조건

- 서울에서 하루짜리 야외 팝업스토어를 열 예정이며, 행사 주간은 다음 주로 이야기됨.
- 장소 후보 유형의 예시는 성수와 백화점 지하, 여의도 더현대임 비슷한 류의 장소를 원함.
- 20~30대가 많이 모이는 곳에 더 관심이 있음.
- 서울 실시간 인구 데이터 API 키를 발급받았음. 키 값은 이 문서와 코드에 적지 않음.
- 아직 정확한 행사일, 브랜드/제품, 후보 주소·공간명, 운영 시간, 예산, 수용 인원은 정해지지 않음.

## 서울 실시간 인구 API에는 연령대와 성별이 있나요?

네. 서울시 실시간 도시데이터 API 명세에는 남성·여성 비율과 연령대별 비율 필드가 있습니다. 20대와 30대 비율을 합쳐 볼 수 있습니다. 다만 이 값은 **그 장소의 해당 조회 시점에 대한 구성 비율**이며, 개별 연령 인원 수 자체는 아닙니다. 장소별 추정 인구의 최소·최대 범위, 자료 갱신 시각, 예측 필드 등도 함께 제공되므로 실제 응답을 확인해야 합니다. API는 주요 핫스팟 이름이나 코드로 조회하므로 원하는 모든 주소가 지원되는 것은 아닙니다. [서울시 실시간 도시데이터 API 명세](https://data.seoul.go.kr/dataList/openApiView.do?infId=OA-21285&srvType=A)

키가 채팅에 원문으로 포함됐으므로 안전을 위해 새 키로 교체한 뒤 사용합니다. 키는 코드에 쓰거나 다시 채팅으로 보낼 필요가 없습니다. Python 코드는 나중에 환경변수에서 키를 읽도록 만듭니다.

## 제안 흐름 한눈에 보기

**① 장소·날짜 후보 구성 → ② 과거 유동인구와 주변 요인 수집 → ③ 시간대별 유동인구 예측 또는 지표 비교 → ④ 야외 운영 위험 확인 → ⑤ 장소·날짜·시간 후보 순위 → ⑥ 상위 후보의 온라인 댓글 주제 분석 → ⑦ 근거와 한계가 포함된 리포트**

핵심은 유동인구 예측과 날씨 안전 판단을 구분하는 것입니다. 날씨는 유동인구를 예측하는 데 쓰면서, 비·강풍·대기질은 야외 개최 가능 여부도 판단합니다. 날씨 효과가 예측값에 반영됐다면 최종 점수에서 같은 효과를 또 크게 더하거나 빼지 않습니다.

## 1. 장소와 행사 날짜 후보를 만든다

### 장소 후보

브랜드와 주소가 아직 없으므로 처음에는 실제 주소 대신 장소 유형/권역을 탐색 후보로 둡니다.

- **성수 후보**: 실시간 인구 API가 지원하는 주요 장소 목록에서 성수 관련 핫스팟이 있는지 확인합니다. 정확한 거리/건물 단위 후보는 서울 상권분석서비스의 도로·건물 유동인구 범위와 맞는지 추가 확인합니다.
- **백화점 지하 후보**: 건물 내부 방문객 수는 공개 데이터만으로 확인되지 않을 수 있습니다. 운영사가 제공하는 건물/층별 통행량이 있으면 우선 검토하고, 없으면 지하철 승하차나 주변 상권을 **대리 지표**로 별도 표시합니다.
- 공개 데이터의 공간 단위가 다른 후보들을 정밀한 같은 척도인 것처럼 직접 순위화하지 않습니다. 비교 가능한 단위끼리 묶고, 매칭이 안 되는 후보는 데이터 공백으로 표시합니다.

### 행사 날짜 후보

“다음 주”는 현재 대화 날짜 기준 2026-10-05~2026-10-11로 해석하되, 가능한 행사는 아직 미정입니다. 월~일의 날짜 후보를 열어두고, 과거 같은 요일·시간대 흐름과 장소 운영 가능일을 비교합니다. 날씨는 날짜가 가까워진 뒤 기상청 예보를 반영하므로, 현시점에서 특정 날의 비 여부를 확정 사실처럼 말하지 않습니다. 전달받은 단기예보 서비스는 시간/격자 단위 상세 예보에 사용하고, 예보 가능 범위를 넘는 날짜는 별도 중기예보로 큰 흐름만 봅니다. 예보와 대기질은 행사 5일 전, 2~3일 전, 전날에 갱신하는 일정을 둡니다.

서울 상권분석서비스는 길/건물 단위 유동인구를 성별·연령대·시간대·요일별로 살펴볼 수 있다고 안내합니다. 자료는 추정치이며, 제공 범위는 분기 단위 데이터가 포함될 수 있으므로 다음 주 특정 날짜의 실시간 과거 시계열을 제공하는지 별도 확인합니다. [서울시 상권분석서비스 상세 분석](https://golmok.seoul.go.kr/intendedOwner/intendedOwnerAnalysis.do), [서비스 제공 범위와 주기](https://golmok.seoul.go.kr/introduce.do)

서울 실시간 도시데이터는 주요 장소의 인구 구성, 혼잡도, 교통·환경 등 현재 정보를 줍니다. 특정 장소의 시간별 데이터를 API로 계속 모으기 시작하면 앞으로의 기록은 쌓을 수 있지만, 그것만으로 지난 계절의 과거 데이터가 생기지는 않습니다.

주변 팝업 정보는 우선 Google 등 웹 검색으로 후보를 찾고, 행사명·주소/장소·기간·원문 링크·확인일을 사람이 검토해 수집합니다. 공식 API나 완전한 공공 목록이 있다고 전제하지 않습니다. 온라인 검색 결과에 안 나오는 행사도 있을 수 있으므로 “검색해 확인된 행사”라고 표기합니다.

## 3. 모델링: 세 가지 질문을 분리한다

### A. 시간대별 예상 유동인구

모델의 정답값은 우선 **그 장소를 해당 시간대에 지나거나 체류한 전체 유동인구 추정치**입니다. 팝업 입장객 수가 아닙니다.

학습에 쓸 수 있는 과거 장소×날짜×시간 자료와 당시 날씨가 충분하다면:

1. 기준선: 같은 장소·요일·시간대의 과거 평균/중앙값
2. 간단한 통계 모델: Poisson 회귀 등 (정답이 0 이상의 인원 수일 때 데이터 분포를 먼저 살펴 선택)
3. 표형 데이터 ML: 데이터 양과 검증 기간이 충분할 때 LightGBM 또는 XGBoost를 추가 비교
4. 날짜 순으로 과거 학습/미래 평가를 나누고, 같은 날의 행이 학습·평가 양쪽에 섞이지 않게 함

다만 실시간 API의 현재 스냅샷만 있거나 상권 자료가 분기/요일 평균뿐이라면, 이 자료로 날씨까지 넣은 날짜별 ML 모델을 학습했다고 주장할 수 없습니다. 이 경우에는 요일·시간대 평균과 공개 지표 비교를 사용하고 결과를 **잠재 유동인구 비교**라고 부릅니다. 학습 기록이 축적되면 그 다음에 ML을 검토합니다. 팝업 입장객 수 모델은 실제 팝업 입장객 수를 정답으로 기록한 데이터가 쌓인 뒤 별도로 만듭니다.

### B. 20~30대 선호 반영

- 같은 장소·날짜·시간의 전체 유동량과 연령별 비율을 함께 얻으면 `전체 유동량 × (20대 비율 + 30대 비율)`로 **20~30대 잠재 유동 규모**를 추정합니다. 두 입력의 기간·장소·단위가 맞을 때만 계산합니다.
- 연령대가 없는 자료에 주민등록 20~30대 인구 비율을 붙이면 방문객 나이를 측정한 것이 아닙니다. 이 값은 인근 거주 인구 기반의 낮은 신뢰도 시나리오로 분리하고, 주 예측값에 섞지 않거나 결과에서 명확히 표시합니다.
- 기본 순위는 20~30대 잠재 유동 규모를 핵심 지표로, 전체 유동량을 보조 지표로 보여줄 수 있습니다. 우선순위는 사용자가 명시한 20~30대 관심을 반영하되 다른 가중치가 임의로 정해진 것처럼 꾸미지 않습니다.

### C. 날씨와 운영 위험

날씨는 유동인구 예측 입력으로 사용하면서, 비/강풍/대기질은 별도의 **운영 가능 조건**으로도 평가할 수 있습니다. 예측 모델이 날씨에 따른 인원 감소를 이미 반영했다면 최종 순위에서 날씨 감점을 또 적용해 같은 영향을 이중 반영하지 않도록 합니다. 대신 운영 위험은 “야외 가능/주의/실내 전환 필요”처럼 별도 표시하고, 기준선은 클라이언트가 정하도록 합니다.

### 장소 점수와 주변 요인

- 대학, 상권, 접근성, 주변 행사 자료를 먼저 유동인구 모델의 입력 피처로 쓸지 검토합니다.
- 이미 예측값에 반영된 요인을 최종 점수에서 다시 더하지 않아 이중 계산을 피합니다.
- 학습 데이터가 부족해 모델 피처로 검증할 수 없는 경우에는 대학 거리, 집객시설 수, 확인된 행사 유무를 별도 설명/시나리오로만 보여주고, 임의 가중치 하나로 정답 순위를 만들지 않습니다.
- 가중치를 사용하면 최소한 기본안과 타깃 연령 우선안 등 몇 가지 시나리오를 나란히 보여 순위가 얼마나 바뀌는지 확인합니다.

## 4. 상위 장소 후보 뒤에 댓글 분석

장소·날짜·시간 후보를 먼저 줄인 다음, 해당 지역의 팝업 경험/관련 카테고리 영상 댓글을 보조적으로 분석하는 것은 가능합니다. 핵심 장소·날짜 예측의 필수 입력은 아닙니다. 브랜드·제품이 없으므로 지금은 특정 상품 구매 의도나 해당 고객군을 지정할 수 없습니다. 이 단계에서 워드클라우드가 보여줄 수 있는 것은 선택한 영상 댓글에서 자주 등장한 표현/주제뿐입니다.

워드클라우드는 맥락, 빈정거림, 긍정·부정, 행동의 실제 발생을 단어 빈도만으로 구별하기 어렵습니다. 그래서 리포트에는 워드클라우드뿐 아니라 대표 주제와 댓글 예시의 맥락, 영상 목록, 조회일, 댓글 수, 수집 기준, 편향 한계를 함께 둡니다. 댓글 주제가 곧 소비 행동이라고 단정하지 않습니다. 댓글 표본을 직접 제공하거나 수동으로 정리하면 수집 API 없이 분석을 시작할 수 있습니다. 여러 영상 댓글을 재현 가능하게 수집하려면 YouTube Data API가 권장되며, 그때 API 키가 필요합니다. 댓글이 비활성화된 영상 등은 수집되지 않을 수 있습니다. ## 5. Python 수집·모델·리포트 구현 순서

1. 키를 코드에 적지 않고 환경변수에서 읽는 기본 구조를 만듭니다. 공공데이터포털 인증키가 URL 인코딩된 형태인지 확인해 중복 인코딩하지 않습니다. 새 키는 채팅이나 소스에 남기지 않습니다.
2. 서울 API에서 실제 지원하는 장소 목록을 확인하고, 후보 핫스팟 1곳을 호출해 연령 필드·갱신 시각·장소명·값 형식을 확인합니다. API 키는 출력/로그에 쓰지 않습니다.
3. API 원응답과 수집시각/갱신시각/장소 코드를 함께 저장합니다.
4. 상권분석서비스에서 후보별 과거 시간대 자료를 받을 수 있는지와 제공 주기를 확인해 같은 기준의 입력 표를 만듭니다.
5. 웹 검색으로 날짜별 주변 행사를 수집하되, 출처 링크와 확인일을 저장합니다.
6. 단위·결측·최신성을 확인합니다. 비교가 안 되는 자료를 자동으로 채우지 않습니다.
7. 충분한 과거 정답 시계열이 있으면 기준선부터 ML까지 순차 비교합니다. 부족하면 비예측형 점수/시나리오 비교로 제한합니다.
8. 후보 날짜가 가까워지면 기상청 예보와 대기질을 갱신하고, 야외 운영 위험을 별도 표기합니다.
9. 상위 후보의 관련 댓글 자료를 선택적으로 수집하고 워드클라우드와 주제 요약을 추가합니다.
10. Python 코드가 표·차트·출처·기준일·가정·한계를 포함한 리포트를 생성하고, 사람이 마지막으로 추천 근거를 검토합니다.

### 범위 예측을 의사결정에 연결

최종 결과는 “예상 10,000명”처럼 단일 숫자로 확정하지 않고, 예를 들어 “예상 유동인구 8,000~12,000명”처럼 범위와 기준을 함께 제시합니다. 실제 시간대별 과거 관측값이 충분하고 과거 검증에서 구간 적중률을 확인할 수 있을 때만 이를 통계적 예측 구간이라고 부릅니다. 데이터가 부족하면 신뢰구간처럼 포장하지 않고 낮음·기준·높음 시나리오 또는 관측 자료 범위로 구분합니다.

Python 모델은 점 예측과 범위 예측을 비교합니다. 기본 회귀 기준선과 함께 자료가 충분하면 분위수 회귀로 낮은 쪽·중앙·높은 쪽 예측(예: 10·50·90 분위수)을 직접 산출하고, 과거 시간 순서 검증으로 범위의 포함률과 폭을 점검합니다. 표본이 작으면 예측 오차로 구간을 보정하는 conformal prediction도 후보입니다. 어느 방식이든 검증 구간에서 실제값이 범위 안에 얼마나 자주 들어왔는지 확인한 뒤에만 “예측 범위”라고 부릅니다. 타깃의 분포와 0 포함 여부에 따라 Poisson 회귀 등 인원 수에 맞는 회귀를 기준 모델로 둡니다.

의사결정 표에는 장소·날짜·시간대별 예측 범위, 20~30대 추정 범위/자료 신뢰도, 날씨 운영 위험과 자료 품질을 나란히 둡니다. 10,000명 수준에 대비한 인력·시설·재고 판단은 범위 하한·기준 예측·상한별 운영 시나리오로 비교합니다. 수용량·예산·재고 비용 같은 클라이언트 기준이 정해지지 않았다면 “최적 선택”이라 단정하지 않습니다. 거리 유동인구와 팝업 실제 방문객은 서로 다른 수치로 분리합니다.

## Python 구현 현황

- `seoul_popup_pipeline.py`: 서울 실시간 도시데이터, 기상청 중기육상예보, 기상청 단기예보 원응답을 JSON으로 저장하고 서울 문화행사 CSV를 검사하는 명령행 도구입니다.

### 현재 모델 결과를 아직 만들지 않은 이유

작업 폴더에는 서울 문화행사 CSV와 비어 있는 입력 양식만 있고, **장소×날짜×시간대 실제 유동인구 정답값은 없습니다.** 따라서 코드는 만들어졌지만 학습·검증을 실행한 적이 없고, 실제 장소별 인원 수나 정확도 수치를 산출하지 않았습니다. 템플릿에는 기준이 되는 필수 열과 예보·주변환경 선택 입력 열이 있습니다. 서울 생활인구는 시간대/250m 격자 추정 체류 인구이고, 분기 행정동 유동인구는 시간대 정답값이 아니므로 단위를 맞춰 사용해야 합니다.

백테스트 기본 보호 기준은 학습 200행·8주, 모델 선택용 롤링 검증 최소 3주입니다. 마지막 미사용 테스트 주까지 포함하면 기본 설정상 대략 12주 이상의 완전한 과거 자료가 있어야 ML 선택을 검토할 수 있습니다. 최근 완료된 한 주를 제외해 롤링 검증으로 모델을 비교한 뒤, 그 주를 마지막 평가용으로 한 번만 사용합니다. 7개 날짜가 모두 있는지는 확인하지만, 전체 센서/장소·운영 시간의 모든 슬롯이 수집되었는지는 예상 수집표가 없으면 확인할 수 없습니다. 과거 기상은 행사 전의 예보 이력을 사용해야 하며, 실제 관측 날씨를 예보 입력으로 사용하면 미래 정보를 미리 쓰는 누수가 됩니다.

## 예측 검증 데이터와 행사 후 성과 평가

이 프로젝트에는 서로 다른 세 가지 종류의 테스트 자료가 필요합니다.

1. **코드가 잘 도는지 보는 테스트 입력**: API 응답 예시, 누락 필드, 잘못된 날짜 등. 실제 행사 성과를 판단하는 자료가 아닙니다. 서울시 문화행사 CSV는 이 단계에서 장소/기간/행사명 처리 코드를 확인하는 입력으로 활용할 수 있습니다.
2. **ML 모델 성능을 보는 과거 테스트 기간**: 예측 시점보다 과거의 실제 유동인구와 같은 시점의 설명 변수(요일, 날씨, 행사 등). 무작위로 행을 섞지 않고 날짜 순서대로 나눕니다.
3. **실제 팝업의 사후 결과**: 행사 시간별 실제 통행/방문 수, 매출 및 구매 건수. 예측을 행사 전에 고정해 두고 끝난 뒤 대조합니다.

### 최근 일주일과 오래전 일주일 중 무엇을 쓸까요?

한 주만 최종 테스트로 고른다면 **학습 자료보다 시간상 뒤에 있고, 실제값이 모두 기록된 가장 최근의 완전한 한 주**가 적합합니다. “최근 7일”이 아직 진행 중이거나 자료가 빠져 있으면 쓰지 않습니다. 학습에는 그보다 앞선 기간만 넣고, 튜닝용 검증 기간도 테스트 주보다 앞에 둡니다. 이렇게 해야 미래 정보를 과거 학습에 섞지 않습니다.

아주 오래된 한 주는 현재 상권·교통·소비·행사 패턴과 다를 수 있어 주된 성능 판단 자료로 부적합할 수 있습니다. 다만 계절 차이 또는 특이 상황에서의 스트레스 점검 자료로는 별도 활용할 수 있습니다. 가능하면 한 주 하나만 택하지 말고, 시간 순서를 지킨 여러 과거 주/날짜 구간을 차례로 테스트하는 **롤링 백테스트**를 하고, 가장 최근 완전 구간은 마지막 미사용 테스트로 남깁니다.

현재 받은 문화행사 CSV에는 행사와 장소 정보는 있지만 시간대별 실제 유동인구, 팝업 입장객 수, 매출이나 구매 건수는 없습니다. 그러므로 이 파일은 행사/장소 피처 또는 코드 테스트용이지 ML의 정답값(test label)은 아닙니다. 서울 실시간 인구 API를 지금부터 모으면 앞으로의 스냅샷은 쌓이지만, 과거 한 주 데이터를 소급해서 얻는 것은 아닙니다. 과거 데이터가 충분하지 않으면 “ML 정확도 검증 완료”로 표현하지 않고, 기준선/설명형 후보 비교 및 데이터 수집 단계로 제한합니다.

### 무엇을 예측하고 어떤 실제값과 비교할까요?

예측 대상의 단위와 실제 측정 단위를 먼저 맞춰야 합니다.

- 모델이 **거리/상권의 시간대별 유동인구**를 예측했다면, 사후에도 같은 거리/상권·같은 시간대의 실제 통행량과 비교합니다.
- 팝업 성과를 보려면 별도로 입구 카운터 등으로 **팝업 방문객 수**를 기록합니다. 거리 통행량은 실제 팝업 방문객 수와 같지 않습니다.
- 20~30대 수를 검증하려면 실제값에도 같은 장소·시간·집계 기준의 연령별 집계가 있어야 합니다. 실제 연령을 수집하지 않았다면 20~30대 세부 예측은 평가할 수 없다고 표시합니다.
- 예측값, 생성 시각, 사용한 입력 스냅샷, 장소/시간 단위, 모델 식별 정보를 행사 전에 저장해 사후 수정 없는 비교 기준을 남깁니다.

### 행사 종료 후 확인할 지표

| 목적 | 지표 | 계산/비교 기준 |
|---|---|---|
| 유동인구 예측 정확도 | 평균절대오차(MAE), 전체절대오차율(WAPE) | 시간대별 예측 통행량과 같은 시간대 실제 통행량의 차이. 분모가 작을 때 불안정한 MAPE는 주 지표로 피함 |
| 20~30대 예측 정확도 | 연령대별 예측 오차 | 실제 연령대 집계가 있을 때만 계산. 없으면 검증 불가 |
| 팝업 방문 성과 | 방문객 수, 구매 건수, 순매출, 판매 수량 | 입장 기록과 POS 자료를 행사 전체 및 시간대별로 합산. 환불/취소 처리 기준을 미리 정함 |
| 방문→구매 전환 | 구매 건수 ÷ 팝업 방문객 수 | “거리 통행량”이 아니라 실제 방문객 수를 분모로 사용 |
| 구매 가치 | 객단가 = 순매출 ÷ 구매 건수, 방문객당 매출 = 순매출 ÷ 방문객 수 | 구매 건수가 0이면 객단가를 계산하지 않음 |
| 사업상 성공 여부 | 순매출·매출총이익·비용 대비 성과, 사전 목표 달성 여부 | 성공 기준과 목표값을 행사 전에 클라이언트와 정함. 행사 뒤에 기준을 바꾸지 않음 |

성과 원인을 해석할 때는 실제 날씨, 운영 시간, 주변 행사, 홍보/광고 집행, 품절, 대기줄, 현장 운영 변경도 같이 기록합니다. 이런 조건은 유동인구 예측 오차 또는 매출 차이를 설명하는 데 도움을 주지만, 매출 증가의 원인이라고 곧바로 단정하지 않습니다. 개인 식별 정보 없이 시간대별 집계값을 우선 보관합니다.

### 사후 분석은 마지막 단계

**사전 예측 저장 → 행사 운영 중 실제 유동/방문/구매 집계 → 예측 오차 계산 → 매출·구매·전환 등 성과 분석 → 오차 원인과 데이터 한계 정리 → 다음 행사 학습 자료로 추가** 순서로 진행합니다. 하루짜리 행사 한 건만으로 모델이 일반적으로 잘 맞는다고 결론 내릴 수는 없습니다. 해당 행사는 1회 사후 검증 자료가 되고, 여러 날짜/장소의 결과가 쌓여야 다음 모델 학습과 일반화 성능 평가가 가능합니다.

### 지금 가능한 결론과 다음 데이터 조건

첫 주의 관측 요약만 보면 **성수는 전체 규모가 크고, 홍대는 20~39세 비율이 높습니다.** 다만 주간 평균 하나만으로 날짜·시간별 ML 성능을 평가하거나 예측 범위를 보정할 수는 없습니다. 내려받은 한 주는 기준선용 탐색 자료로 보관하고, 서울시 과거 파일을 추가 확보해 최신 완전한 주를 최종 테스트로 남긴 채 여러 이전 주의 롤링 검증을 구성해야 합니다. 기존 모델 기본 조건(최소 8주 학습 + 여러 검증 주 + 최종 테스트 주)을 채우기 전에는 ML 성능이 확인된 것으로 표현하지 않습니다.

팝업 방문객 수를 “약 1만 명”처럼 예측하려면 장소·운영 시간에 맞춘 실제 입장 카운터 자료가 추가로 필요합니다. 현재 자료로 산출 가능한 것은 후보 권역의 잠재 체류인구 비교입니다.
